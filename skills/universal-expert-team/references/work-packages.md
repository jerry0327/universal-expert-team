# Work packages and acceptance

Use this reference for complex delegation, shared writes, cross-package
dependencies or resumed work. Keep records in the existing task plan or log;
do not manufacture an extra document for every small assignment.

## Compact task contract

Adapt this shape; fields are requirements to consider, not a mandatory user form.

- **Task/attempt:** stable objective identity and current attempt.
- **Outcome:** a concrete answer, artifact, change or decision, with audience.
- **Inputs:** authoritative sources, accessible paths/URLs and relevant versions.
- **Scope:** allowed actions/resources, exclusive writer or read-only status,
  excluded actions, delivery destination and any already-authorized release.
- **Dependencies:** required input versions, handoff interfaces and integration
  owner; identify what can proceed independently.
- **Acceptance:** observable criteria and minimum sufficient evidence, including
  required independence and intended operating/rendering environment.
- **Worker:** actual agent identity, requested and observed settings separately,
  own-channel evidence where needed, and allocated descendant seats.
- **Return:** result, artifact references, checks actually performed, material
  uncertainties/defects and blockers; route consequential changes to coordinator.

A concise brief can satisfy these fields in a paragraph. Use a table or structured
record only when it reduces ambiguity. Never require a worker to reveal private
chain-of-thought; request sources, reasoning summaries and reproducible findings.

## Design from outputs, not job titles

Identify what can be produced independently, what expertise changes decisions,
and which failure needs a separate perspective. Combine compatible roles;
separate conflicting writes and genuinely independent judgments. Use a planning
worker for difficult decomposition when its proposal changes execution; let it
return work packages, interfaces, risks and acceptance, not a ceremonial roster.

A package is too small if coordination costs exceed its useful independent work.
A package is too large if its owner cannot verify its boundaries or complete it
without recurring micromanagement. Do not turn either heuristic into a hard size,
headcount, time or token threshold.

## Define acceptance before the result

Express required behavior in the user's terms. Choose checks that could disprove
success. Examples of evidence types, not mandatory domain categories:

| Property at stake | Evidence that can support acceptance |
| --- | --- |
| Factual or quantitative correctness | Traceable authoritative sources, compatible definitions/denominators, reproducible calculations |
| Reasoning or decision quality | Assumptions, relevant alternatives/counterexamples, justified resolution of material disagreement |
| Required coverage | Mapping from the requested scope/questions to completed content and explicit gaps |
| Function and interaction | Representative actual execution against requirements and meaningful boundary/failure cases |
| Readability or visual layout | Inspection of the actual final rendering, relevant pages/screens and target audience needs |
| Persistence or external change | Actual save/action receipt and appropriate readback of the exact destination/version |
| Overall integration | Consistent interfaces, numbers, terminology, dependencies, narrative and final user-facing state |

Do not invent thresholds or silently weaken criteria to obtain a pass.
If a requirement is subjective, derive a concise rubric from the user's examples
or objective (clarity, coherence, completeness, suitability), then assess it
explicitly. Avoid claiming measurable perfection.

## Autonomous execution and communication

Let owners choose routine implementation details within their scope. Workers may
ask peers focused interface questions and send evidence directly when supported;
they must not privately widen shared scope or claim unallocated resources.
Escalate consequential dependencies, conflicting source interpretations and
permission needs. Root need not relay every exchange.

For direct worker delivery, verify actual destination access/persistence when
relevant and tell Root where the artifact is. Direct delivery does not excuse a
missing package in the final integrated result or imply other workers can access
that destination.

## Changes and handoffs

Link findings and corrections to current inputs/attempts. Invalidate only checks
whose premises changed. Preserve accepted unaffected work; isolate stale or late
results rather than overwriting current work. On cancellation, stop the affected
tree through available controls and reconcile outstanding operations; cancellation
does not prove a write stopped.

After context loss, reconstruct intent, mode, accepted outputs, open defects,
ownership and dependencies from verified records. Follow the bundled runtime guidance for
live capacity, worker addressability and unsettled operations. Summaries are a
starting point, not proof that an external action succeeded or failed.
